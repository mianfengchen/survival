# 赐福系统（草案）

对应 `design-notes.md` 第 2 阶段：单角色 + 其余 36 位角色转为赐福提供者。
叙事依据见 `story-framework.md`「精灵与赐福」——那些力量本就在小精灵体内，随战线推进逐步苏醒。

## 设计目标

1. 让 36 位角色从"换皮角色"变成**成长内容**，既有人设 / 技能 / 档案全部保留。
2. 取代现有的角色选择流程，并清理 `battleRule` / `getCharacterAllowedSkillIds` 的既有缺陷。
3. 制造**出战前的取舍**：拥有很多，但能带的很少。
4. 给"可重复刷区域"一个明确的目标。
5. 不抽空局内变量——局外决定带什么，局内决定怎么长。

## 一、赐福的三层结构

每位提供者的赐福分三层，由浅到深。分层的目的是让 36 份赐福形成**纵深**，
而不是 36 个一次性的二元解锁。

| 层 | 名称 | 内容 | 既有素材 |
| --- | --- | --- | --- |
| 一 | **初赐** | 解锁该提供者的签名技能，进入可携带池 | `CHARACTER_LIBRARY[].skillId`，36 个技能均已实现 |
| 二 | **深赐** | 分档解锁该技能的专属成长，进入局内升级池 | `SKILL_LIBRARY[].exclusiveUpgrades`，**已全部写好** |
| 三 | **本源** | 该提供者的**特性**：作用于整套构筑的被动，不限于那个技能 | 需新建，建议仅少数提供者拥有 |

### 关于「本源 / 特性」为何值得做

此前讨论否决过 VS 式的"角色特性"，理由是：**一条弱被动挂在共享池上，投入感与分化度都不够**，
构筑最终收敛到少数最强解。

本源不同，差别在于**数量关系**：

- VS 式：选一个角色 = 固定拿到一条被动。单一、不可组合，所以寡淡。
- 本源：从几十份里**同时装备数条**，彼此叠加与冲突。

同样是"特性"，前者是加法且唯一，后者是组合且稀缺。组合空间才是构筑深度的来源——
这与「内容会被消耗，系统会被重玩」的诊断一致。

**授权建议：本源只给一个精选子集（约 12 份），不要 36 份全给。**
36 条会改变整套构筑运作方式的被动，既难平衡也难写出差异；
其余提供者只给初赐 + 深赐即可。这把工作量压到可控范围。

## 二、获取渠道

四条渠道，各自承担不同职责，不重复。

| 渠道 | 产出 | 职责 |
| --- | --- | --- |
| **A. 区域首次解放** | 初赐 | 主线节奏的确定性来源。推进即必得，不靠运气 |
| **B. 研究所兑换（植物能量）** | 初赐 / 深赐 | 玩家自主权与追赶机制。想要哪份就去换，不受地图进度卡死 |
| **C. 重复部署某区域积累共鸣** | 深赐 | 给"可重复刷"一个目标：刷这张图是为了深化这份赐福 |
| **D. 该赐福的专属挑战** | 本源 | 要求用特定构筑达成，制造"换个打法"的长线目标 |

要点：

- **A 保证下限**：正常推进就能拿到足够用的赐福，不会卡住。
- **B 复用现有 UI**：`技能工坊` 与 `专属工坊` 已经是这个形态，改为按赐福组织即可。
- **C 让重复刷有方向**：共鸣值绑定具体赐福，而不是泛泛地攒通用货币。
- **D 是长尾**：挑战条件天然要求特定构筑，正好是此前列入长尾清单的
  「要求特定构筑的成就」。可以最后做。

## 三、槽位：稀缺才有取舍

**没有槽位上限，整套系统就不成立**——36 份全带 = 零决策。

| 槽位 | 初始 | 上限（建议） | 说明 |
| --- | --- | --- | --- |
| 技能槽 | 1–2 | 4–6 | 出战前从已解锁技能中装备 |
| 本源槽 | 0 | 2–3 | 与技能槽独立计数 |

- 槽位本身作为成长节点开放（主干推进 / 植物能量兑换），是一条贯穿全程的长线目标。
- **精灵箭术（`elfArrow`）为小精灵自身力量**，恒定可用，不占技能槽。
- 局内升级池只从**已装备**的技能中抽取等级与专属——这是局外与局内的分工边界。

## 四、与三条路线的交互

槽位稀缺让三条路线自然长出不同的装配哲学，无需额外规则：

| 路线 | 装配倾向 | 原因 |
| --- | --- | --- |
| **融合** | **广度**：带多个可融合的技能 | 融合需要 2+ 技能作为素材 |
| **异化** | **深度**：少而精，把少数技能异化到底 | 异化是在单个技能上叠加强化与代价 |
| **神化** | **规整**：成套、同主题、按序 | 契合秩序侧的"接受它的形状" |

这项交互是免费的——它来自槽位稀缺与分支机制本身，不需要为每条路线单独写装配规则。

## 五、节奏与门槛

- **开场不能干**：教学区与前几个区域的初赐给得快、给得便宜。
  首次进入时只有一个技能是可以的，但不应持续到第三、四场。
- **不要求集齐**：一套能打的构筑应该在拿到 4–6 份赐福时就成立，
  而不是必须打完 36 个区域。集齐是收集目标，不是通关门槛。
- **后段放缓**：深赐与本源是后段的消耗项，用共鸣与挑战拉长，而不是用涨价拉长。

## 六、货币结构

- **植物能量（全局共享）**：所有赐福解锁与槽位开放的通用货币。
  **不要**按路线或按提供者拆分货币——那会让"换一条分支试试"变成从零重刷，劝退。
- **共鸣（按赐福计）**：部署对应区域 / 使用该技能积累，只能用于深化该份赐福。
  它是"定向"货币，让重复刷有具体指向。
- **露金**：保持现状，纯局内，不参与赐福。

## 七、数据结构草案

定义侧（`garden-data.js`，复用角色 id）：

```js
{
  id: "sunblossom",             // 复用 CHARACTER_LIBRARY 的 id
  skillId: "solarPulse",        // 初赐解锁的技能
  sourceRegionId: "region-12",  // 渠道 A：首次解放该区域可得初赐
  unlockCost: 180,              // 渠道 B：研究所兑换价（沿用 SKILL_LIBRARY.unlockCost）
  resonanceMax: 3,              // 渠道 C：共鸣档数，对应深赐解锁进度
  essence: {                    // 渠道 D：本源，仅精选子集拥有
    id: "sunblossomEssence",
    name: "灿光共鸣",
    description: "……",
    challenge: "以向日脉冲为主技能通过任意区域",
  },
}
```

存档侧（`storage.js`，接入现有 `world` 与 merge 流程）：

```js
world.blessings = {
  sunblossom: { granted: true, resonance: 2, essence: false },
}

world.loadout = {
  skillIds: ["solarPulse", "dewGarden"],  // elfArrow 不入列，恒定可用
  essenceIds: [],
  skillSlots: 2,
  essenceSlots: 0,
}
```

映射关系：

- `world.unlockedCharacters` → 迁移为 `world.blessings`（语义从"可选角色"变为"已获赐福"）。
- `unlocks.skills` / `unlocks.exclusives` → 保留，作为赐福层的实际落地结果；
  深赐解锁即写入 `unlocks.exclusives`，局内升级池无需改动即可生效。
- `world.selectedCharacterId` → 废弃，由 `world.loadout` 取代。

## 八、需要处理的既有代码问题

1. **`getCharacterAllowedSkillIds()` 当前返回所有已解锁角色的技能合集**，与所选角色无关；
   `battleRule` 字段从未被判断。本阶段应整体替换为读取 `world.loadout.skillIds`。
2. **`flyingSword` 带 `startsUnlocked: true`**，与赐福模型冲突（它不属于任何提供者）。
   需决定：转为小精灵的第二份固有技能、指派给某位提供者、或退役。
   它已有完整专属树（虹光穿透 / 寻敌剑心 / 巨刃奇袭 / 亮闪闪 / 闪亮亮），退役会浪费内容。
3. **区域奖励当前为 `character | landscape` 二选一**（`createRegionReward`）。
   需随第 3 阶段地图重构一并改为多奖励轨：赐福 / 景观 / 槽位 / 时装。
4. **`CHARACTER_ARCHIVE` 未接线**（仅 1 条，引用的 `designs/archive/` 不存在）。
   赐福系统正好是它的归宿：赐福详情页展示提供者档案。

## 九、实施分期

| 期 | 内容 | 价值 |
| --- | --- | --- |
| **P1 ✅ 已实装** | 初赐 + 技能槽 + loadout 存档；移除角色选择流程 | 最小改动即让系统成立；角色鸡肋问题当场解决 |
| **P2** | 深赐接入现有 `专属工坊` + 共鸣值 | **几乎是免费的**：专属数据已全部写好，只需换成按赐福组织 + 加共鸣进度 |
| **P3** | 本源 + 本源槽 + 挑战条件（精选 12 份） | 构筑深度的主要来源，但需新建内容，放最后 |

P1 不依赖地图重构，可立即进行；P2 复用既有数据，成本最低；
P3 建议与第 4 阶段（融合）前后衔接，因为本源与融合共同构成构筑深度。

## 十、风险

- **节点膨胀**：36 份 × 三层最多约 100+ 个解锁节点，grind 感会过重。
  缓解：本源只做精选子集；深赐沿用既有专属（无需新内容）；初赐走确定性获取。
- **槽位数值敏感**：技能槽给到 6 以上时，构筑趋同风险上升（什么都能带 = 没有取舍）。
  建议保守起步（4），观察后再放。
- **本源平衡**：会改变整套构筑运作方式的被动最难平衡，是本系统唯一真正的高风险项，
  故放在 P3 且限量。

## 十、P1 实装记录

已完成，以下为落地结果与实装中确定的细节。

### 数据与存档

- `garden-data.js`：新增 `BLESSING_LIBRARY`（由 `CHARACTER_LIBRARY` 派生 36 份），
  每份含 `skillId` / `innate` / `extraSkillIds` / `sourceRegionId` / `resonanceMax` / `essence`。
  另有 `PROTAGONIST_BLESSING_ID`、`INNATE_SKILL_IDS`、槽位常量与 `getSkillSlotCost()`。
- `createRegionReward` 的奖励类型由 `character` 改为 `blessing`，
  映射关系为「区域 index i ↔ `CHARACTER_LIBRARY[i]`」，与 `sourceRegionId` 互为镜像（已加测试锁定）。
- `storage.js`：存档版本 3 → 4。`world.unlockedCharacters` / `world.selectedCharacterId`
  在 merge 时被解构剔除，并迁移为 `world.blessings`；新增 `world.loadout`。
  旧存档可无损升级（已测）。
- 本源字段（`blessings[].essence`、`loadout.essenceIds`、`loadout.essenceSlots`）均已预留，
  P3 落地时无需再做存档迁移。

### 实装中确定的细节

1. **飞剑术默认装配。** `flyingSword` 不属于任何提供者，现挂在主角 `extraSkillIds` 下，
   并在默认装配里预置。理由：沿用旧版 `settings.initialSkillId = "flyingSword"` 的手感，
   同时避免开局只有一个技能。它占技能槽，可自由卸下。归属仍为待定项。
2. **授予时自动填充空槽。** 获得新赐福时，若技能槽尚有空位则自动装备；
   槽位已满时只授予、不顶替已装配的内容（已测）。
3. **起始技能取首个可用技能**，固有技能 `elfArrow` 永远在列首，因此不会出现无技能可用的局。
4. **技能槽扩容**放在研究所，用植物能量购买：
   价格 `240 + (当前槽位 − 2) × 220`，上限 6 槽。
5. **专属研究的门槛改为「已获赐福」而非「已装配」**，避免为了研究专属而被迫改装配。
6. 局内可用技能完全由装配决定：`allowedSkillIds = 固有技能 + 已装配技能`，
   未装配的技能不会出现在升级池。这正式取代了原先
   `getCharacterAllowedSkillIds()` 返回「所有已解锁角色技能合集」的缺陷行为。

### 顺带修掉的既有问题

- `battleRule` 摆设字段与 `getCharacterAllowedSkillIds()` 的缺陷实现已随角色选择流程一并移除。
- 发现并记录：原 `createRegionReward` 的景观分支**不可达**
  （需要 `regionIndex >= 36`，而最大仅 35），因此景观从未真正被授予过——
  这与「景观加成在 `game.js` 中无任何引用」是同一件事的两个侧面。
  景观将在第 3 阶段随地图重构改为分支终点奖励。

### 验证

- 8 个源文件 `node --check` 全通过。
- 具名 import / export 全图可解析，无残留引用。
- 两套临时测试共 58 项全部通过（已按约定删除脚本）：
  旧存档迁移、槽位裁剪与去重、固有技能不占槽、未授予技能装不上、
  授予时自动填槽、满槽不顶替、扩容上限、本源在 P1 保持锁定、
  赐福↔区域映射自洽、装配 → 出战配置 → 局内技能池贯通。
- DOM id 与 `main.js` 查询一致（仅移除 `prepSelectedCharacter` / `warCharacterOptions`，
  新增 7 个装配与槽位相关 id）。

## 十一、本源结构（P3 细化）

先定本源的结构，是因为它决定 P1 的存档字段与装配界面要预留什么。
本节只定**结构与分类**，不定具体数值。

### 与「特殊增益」的分工（必须先分清）

代码中已有 `SPECIAL_BOON_LIBRARY`（多重 / 虚化 / 连锁 / 残响回旋 / 蓄力 / 杀心 /
冰霜花苞 / 冰棘 / 余烬之种 / 灵魂剥离…），它们已经是"改变构筑运作方式"的效果，
质感正是本源想要的。因此本源**沿用同一套实现钩子**，但职责必须区分开，否则两者重复：

| | 特殊增益（已有） | 本源（新增） |
| --- | --- | --- |
| 来源 | 局内击杀精英，**随机**给 | 局外赐福，**自选**装备 |
| 范围 | 仅本局 | 跨局，出战前确定 |
| 作用对象 | 多为触发型 proc（命中 / 击杀 / 受伤时） | **整套构筑的规则**（流派、转化、状态、契约） |
| 职责 | 提供**运气**与单局高光 | 提供**计划**与构筑身份 |

一句话：**特殊增益是"这局运气好"，本源是"我这套想怎么打"。** 两者可以共存，
甚至可以互相引用（例如某本源专门强化特殊增益的触发）。

### 本源的五类

分类标准是"它改变什么"，每类都有既有代码钩子，不是空想。

| 类 | 作用 | 可用钩子 |
| --- | --- | --- |
| **A 流派专精** | 强化某一类技能，削弱其他类 | `PROJECTILE_COUNT_SKILLS` / `SUMMON_COUNT_SKILLS` 已存在；场地类可按 `spawnField` 归类 |
| **B 转化** | 把一种收益换成另一种（溢出转伤害、数量转穿透、冷却转伤害） | `projectileCountBonus` / `cooldownScale` / `projectileSizeMultiplier` / `rangeMultiplier` |
| **C 状态联动** | 让状态之间产生反应（易伤放大、灼烧蔓延、麻痹触发暴击） | 既有状态：减速 / 灼烧 / 麻痹 / 易伤 / 流血 / 寄生 |
| **D 风险契约** | 接受一个缺陷换取大幅强化 | `majestyStacks` / `majestyMultiplier` 已实现；`monsterPressure` 是现成范式 |
| **E 结构** | 改变本局的框架规则（升级池、重抽、特殊增益触发、槽位） | `buildUpgradeChoices` / `rerollLevelChoicesToPassives` / `SPECIAL_BOON_LIBRARY` |

**B 类是数值方向的落点**：`design-notes.md` 里"边际转化、渐近而非撞墙"的原则，
正是靠 B 类本源提供给玩家的主动选项——玩家自己决定把溢出的覆盖换成什么。

**C 类是第 5 阶段的前置**：状态联动规则表做好后，C 类本源就是它的开关与放大器。

这样授权量从 36 条降到 12 条，且每条都有既有机制可依托。

### 叠加与冲突规则

- **同类可叠，但收益递减**（两个 A 类流派专精叠加不应等于双倍）。
- **互斥关系显式声明**：例如投射专精与召唤专精互斥，装备时直接禁止，而不是让它们互相抵消。
- **本源不设数值硬上限**，遵循 `design-notes.md` 的数值方向：
  靠槽位稀缺与互斥关系控制分布，而不是 clamp。
- **三条路线的交互**：异化 / 神化会为本源追加变体（强化 + 机制代价），
  融合则允许本源之间产生额外联动。该层留到第 4 阶段。

### 数据结构

定义侧，挂在赐福定义的 `essence` 字段上（见第七节）：

```js
essence: {
  id: "clockivyEssence",
  name: "钟域共鸣",
  category: "status",            // a:category | b:convert | c:status | d:contract | e:structure
  description: "……",
  exclusiveWith: ["lotuskeeperEssence"],  // 互斥本源 id
  challenge: {                   // 渠道 D 的解锁条件
    type: "skillClear",          // 以该技能为主通过任意区域
    skillId: "clockIvyLash",
  },
}
```

存档侧：P1 即需预留 `world.blessings[].essence` 与
`world.loadout.essenceIds` / `essenceSlots`，哪怕 P3 之前一直为空 / 为 0。
这样 P3 落地时不需要再做一次存档迁移。

### P1 必须预留的东西

| 字段 | P1 行为 | P3 行为 |
| --- | --- | --- |
| `world.blessings[id].essence` | 恒为 `false` | 挑战达成后置 `true` |
| `world.loadout.essenceIds` | 恒为 `[]` | 装备的本源 id |
| `world.loadout.essenceSlots` | 恒为 `0` | 2–3 |
| 装配界面 | 只渲染技能槽区域 | 增加本源槽区域 |
