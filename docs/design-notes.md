# 设计决议记录

本文件记录设计讨论中**已确定**、**已否决**、**待定**的结论，以及后续阶段计划。
与 `systems.md` / `skills.md` 的区别：那两份描述"系统是什么"，本文件记录"为什么这么定、以及还没定什么"。

> 注意：截至本文件写入时，`systems.md`、`skills.md`、`Readme.md` 与代码已有明显漂移
> （低报了技能数与角色实现程度，技能改名未同步）。文档同步见「阶段计划 · 第 0 阶段」。

## 现状基线（基于代码核实）

- 技术栈：原生 JS，无构建、无依赖安装（无 `package.json`），Pixi 走 CDN，带 PWA 外壳。
- 规模：约 2 万行；`game.js` 9721 行、`pixi-renderer.js` 4270 行、`app.css` 2512 行。
- 技能：`skills.js` 共 **37 个**技能，各有 `statsByLevel`（maxLevel 5）与 `exclusiveUpgrades`；
  每个技能在 `game.js` 都有真实的 `cast*` 实现，不是占位。
- 战役：36 区域（6×6 邻接解放）、36 Boss、36 区域专属亲族怪、5 档战争难度。
- 局内：10 种波次类型 + 临时词条、波间休整、露金商店、升级三选一、精英特殊增益。
- 元进度：天赋、技能工坊、专属工坊、6 类图鉴、`localStorage`（version 3，带 merge 迁移）。

### 已核实的缺陷

1. **景观是死数据**：`LANDSCAPE_LIBRARY` 的 12 个景观会作为区域奖励解锁并显示，
   但 `game.js` 中不存在 `unlockedLandscapes` / `LANDSCAPE_LIBRARY` 的任何引用，解锁后无实际效果。
2. **角色之间无差异**：`getCharacterAllowedSkillIds()` 返回的是**所有已解锁角色的签名技能合集**，
   与当前选择的角色无关；`battleRule: "allUnlockedSkills"` 字段在 `game.js` 中从未被判断，是摆设。
   实际效果是 36 个角色除初始技能不同外玩法完全一致。
3. **角色档案未接线**：`CHARACTER_ARCHIVE` / `getCharacterArchive` 从未被 `main.js` 引用；
   36 个角色中仅写了 1 条（向日花灵），其引用的 `designs/archive/` 目录不存在。
4. **害虫星球是纯占位**：`#bugPlanetScreen` 仅有一段「保留为后续章节」文案与返回按钮。
5. **离线能力名不副实**：Pixi 走 CDN，PWA 首启必须联网。
6. **工程化为零**：无构建、无测试、无 lint；`game.js` 单文件已到维护临界点。

## 核心诊断

> **内容会被消耗，系统会被重玩。**

- 内容型新鲜感（新技能、新进化、新 Boss、新区域）是线性的、会被看完、必然耗尽。
- 系统型新鲜感（技能交互、构筑组合、每局重随规则、操作精进）是组合式的，不会被"看完"。

本项目的现状是**内容量极其充足、系统层很薄**：37 个技能互不交互、角色无差异、
每局规则相同。因此持续加内容无法解决"每局体验雷同"的问题——这是用内容治系统的病。

推论：37 个互不相干的技能 = 37 份体验；37 个会互相反应的技能 = 成百上千种组合。
**同样的内容量，寿命差一个数量级。**

另一个结论：幸存者品类的正常寿命是有限的（同类作品普遍 20–40 小时）。
目标应是「前 20 小时非常好 + 给少数深挖玩家留一条长尾（难度阶梯 / 排行榜）」，
而不是追求无限可玩。

## 已确定的方向

### 角色系统：单角色 + 赐福

- 改为**单一主角**（小精灵，契合「花园最后一只精灵」的既有前提）。
- 其余 36 个角色转为**赐福提供者**：通过单局通过或其他方式获得其赐福，从而解锁对应技能。
- 价值：既有的 36 套人设 / 称号 / archive 全部作为内容资产保留，不浪费；
  同时消灭「角色只是换初始技能」的问题，角色轴与技能轴合并为一条连贯的成长线。
- 副作用：角色选择界面取消；`battleRule` 与 `getCharacterAllowedSkillIds` 的现有缺陷一并消失
  （当前代码的既成事实正式成为设计）。

### 景观：元地图层的光环 + 可携带能力

- 作用层级：**元地图层**（进入区域 → 该局整体吃到光环修正），不做战斗场景内的实际地形区域。
- 规则：**完整版**只在该景观主场光环内生效（节点最强，按地图距离衰减）；
  **简化版**解锁后随身携带、全图永久生效但强度很弱。
- 能力形态：被动 / 主动 / 光环均为备选，**具体未定**。
- 价值：奖励从「+5% 移速」变为机制，有记忆点；同时是数值护栏——
  全局只拿弱化版，强力版被地理锁在主场，power 上限被「去哪打」分流，而非一刀切砍伤害。
- 可选杠杆：强光环区域同时抬高敌人密度（复用现有风险收益机制），保持张力。

### 地图：主干 + 分叉

- 形态为**一条主线流程 + 分支**（非严格二叉树）。
- 分支终点解锁景观；沿分支越深入，离景观越近，受光环影响越强（「越靠近越强烈」直接落在图距离上）。
- 分支可承载不同主题地图类型：防守、挑战、Boss 战等。
- 多条奖励轨并行：景观 / 技能 / 技能强化 / 时装。
- **已解放区域可重复部署刷取**。
- 实现效率要求：主题地图类型应尽量复用现有波次机器
  （防守 ≈ 强化版 `坚守`，挑战 ≈ 词条叠加，Boss 战 ≈ 现成 Boss 流程），不作为新模式另写。

### 故事框架：结构性骨架，而非装饰

- 剧情**不只是装饰**：第 4 阶段的三条成长分支（融合 / 异化 / 神化）对应三个剧情方向，
  结局联动最后一关。因此故事框架决定下游分支形状，必须先定。
- 硬性约束：**不做与地图拓扑一一对应的线性剧情**（此前已踩过这个坑，地图一改剧情就对不上）。
- 范围控制：只写「一页前提 + 几条主题轴 + 三个结局触发条件」，不写剧本。
- 叙事预算投向环境叙事：分支主题、景观 lore、角色 / Boss 解锁时的 flavor —— 叙事作为挂在内容上的
  可发现碎片，随内容自动增长，不需与地图结构同步。

### 数值：控制分布，不设硬性上限

power 的成长维度分为两类：

- **安全维度**：伤害、穿透。杀得再快，走位与闪避层仍在，爽感保留。
- **危险维度**：频率（冷却）、数量（count）、范围/体积。它们消灭的是"空隙"，而空隙即玩法本身。

现状是狂堆危险维度（`PROJECTILE_COUNT_SKILLS` / `SUMMON_COUNT_SKILLS` + 特殊增益加 count，
冷却可叠到近乎无间隔），所以单技能即可铺满屏。

**核心原则：不设硬性上限。** 不要出现"冷却最多 60%""count 最多 8"这类 clamp——
硬墙会掐死"梦想构筑"，玩家一眼看到天花板就失去堆叠动力。
允许单局在特别顺利时达成相当夸张的构筑，**只要它不是每局都能达成**。

**要控制的是概率分布，不是天花板。** 期望值压低，方差保留；
"神之一局"应当偶尔发生，并且正是这种局的回报所在。

具体手段（按优先级）：

1. **渐近公式替代 clamp。** 用 `实际冷却 = 基础冷却 / (1 + 急速)` 这类形式替代减法 + 上限：
   急速 100% → 冷却减半，300% → 四分之一，永远不会到 0，但极端堆叠依然看得见、摸得着、很爽。
   count 与体积同理，用每层递减（第 N 层收益低于第 N−1 层）而不是到某层直接截断。
2. **边际转化，而不是撞墙转化。** 溢出转伤害应随饱和度**渐进**介入
   （越接近铺满，新增的覆盖越多地折算成伤害），而不是到达上限后突然切换。
   玩家感知应是"收益换了形式"，而非"被拦住了"。
3. **供给侧控制。** 单局能拿到的覆盖类强化**期望数量**压低：
   降低出现权重、同类重复出现时权重递减或涨价。
   夸张构筑因此需要运气堆叠，自然稀有，不需要规则禁止。
4. **多源乘算。** 极端覆盖要求多个独立来源同时对齐
   （技能等级 + 专属 + 特殊增益 + 景观主场 + 融合）。
   需要全部凑齐这件事本身就使它罕见，而凑齐的那一局会非常难忘。

全屏覆盖的定位：**不是默认基线，而是运气与选择共同促成的高光时刻**；
融合 / 神化 / 景观主场是它的正式入口，随机堆叠是它的意外入口——两条都保留。
- 敌人侧杠杆优先级：杂兵**不堆血**（会让伤害手感发虚），难度来自密度、漏怪惩罚、
  捣乱怪、位置否定、带弹幕的威胁怪、方向/护盾减伤怪；
  精英与 Boss 才应该厚且带机制（也是高伤害构筑的发光处）。
- 数值重做挂靠在融合阶段：基础技能覆盖封顶，突破覆盖靠融合 / 神化 / 景观，
  使"削弱"转化为"解锁条件"，不损吸引力。

## 已否决 / 已搁置

| 方案 | 结论 | 理由 |
| --- | --- | --- |
| 景观做成单纯属性加成（+5% 移速一类） | 否决 | 太普通、无记忆点；且无法作为数值护栏 |
| 转向装备 / 合成内核（WC3 守图路线） | 搁置 | 口味契合（确定性憋装的掌控感），但与现有形态距离远；WC3 守图本身重复可玩性差（出装路线固定、局间无变量、乐趣多来自联机与首通） |
| 共享技能池 + 角色特性（VS 式弱被动） | 否决 | 体验不突出：特性通常只是小幅乘数，挂在共享池上投入感与分化度都不够，构筑最终收敛到少数最强解 |
| 每角色一棵完整独立技能树（灵魂石式），保留 36 角色 | 否决 | 36 棵树必然每棵都浅；授权与平衡成本过高。该模型仅在角色砍到 8–12 时成立 |
| 局内只保留属性拾取 | 否决 | 技能获取是本品类最大的单一变量源，抽走后每局会更雷同、升级时刻失重、结果在进场前就定了 |
| 仅靠技能进化延长寿命 | 不足 | 进化仍是内容型新鲜感，体验过即耗尽；需系统型增长（见「核心诊断」） |
| 线性 / 分支剧情与地图拓扑对应 | 否决 | 维护陷阱，地图一改即对不上（已实际发生） |

## 待定

- 景观能力的具体形态（被动 / 主动 / 光环）与试点景观（建议日晷花坛，机制最直观）。
- 地图规模：分支条数、景观终点数量、区域总数是否从 36 缩减。
- 融合系统的授权方式（见下，倾向标签驱动 + 少量手工招牌）。
- 局外成长的货币结构（倾向全局共享，避免换角色 / 换分支从零重刷的劝退感）。
- 本体异化 / 神化是否带机制代价（倾向带，但应是"换一种玩法"而非单纯变弱）。
- 分支占优的判定口径：节点数占比、是否允许中途转向、转向代价。
- 异化深渊 / 神化圣堂的正式命名与视觉语言（现为工作名）。
- 害虫星球：已定为主线侵略方 + 四条结局的统一后续钩子，**本阶段不做**。
  具体形态（续章 / 无尽模式 / 排行榜）待后续决定。

序号沿用讨论中的顺序，补入一个前置阶段与两处缺口。

- 文档同步：`systems.md` / `skills.md` / `Readme.md` 更新到真实的 37 技能 / 36 角色全实现状态，技能改名对齐。

### 第 1 阶段 · 故事框架

**草案已产出：`story-framework.md`（v2，四方力量版）。**
不必立即写入游戏，但需足以支撑第 3、4 阶段的取舍。约束见「已确定的方向 · 故事框架」。

框架要点：

- **四方力量**：植物花园（主角方）、害虫星球（侵略者 / 主线敌人）、
  异化深渊与神化圣堂（两个第三方诱惑者，互为对手，但都不容许超越自己的力量出现）。
- **三次选择 → 四条结局**：不选 / 异化 / 神化 / 融合。击败虫王后触发隐藏结局，
  由对立阵营（或两方联合，针对融合）前来讨伐，击败使者后解锁对应结局。
  难度天然成阶梯：存续 < 阵营结局 < 新生。
- **小精灵 = 花园集体力量的载体**（替代花心设定）。这解释了赐福 / 其他角色技能的解锁机制：
  那些力量本就在体内，随战线推进逐步苏醒。
- **异化 / 神化会反作用到角色本体**，随进程加深（外观必然，机制代价待定）；
  技能侧分「局外直接投入（定结局）」与「局内结晶 / 圣痕（仅本局，保留每局变量）」两条路径。
- **混合 Boss 语法**：Boss 原为花园守卫血脉，被三方各自重塑 → 害虫类 / 异化类 / 神化类。
  既复用现有植物系 Boss 美术，又让内容量按「族系 × 混合类型」扩张。

已废弃：花心概念、轮回 / 终局 Boss 为另一座花园的镜像。

### 第 2 阶段 · 单角色 + 赐福解锁

**细化方案见 `blessing-system.md`；其中 P1 已实装**（初赐 + 技能槽 + loadout 存档，
角色选择流程已移除，存档版本 3 → 4 并支持旧档无损迁移）。
实装记录与实测结论见该文档第十节。

- 主角固定为小精灵；36 角色转为赐福提供者。
- 赐福分三层：**初赐**（解锁技能）/ **深赐**（解锁该技能专属，沿用既有 `exclusiveUpgrades`）/
  **本源**（作用于整套构筑的特性，建议仅精选约 12 份）。
- 四条获取渠道：区域首次解放（确定性）、研究所兑换（自主权）、
  重复部署积累共鸣（给可重复刷一个目标）、专属挑战（长尾）。
- **槽位稀缺是系统成立的前提**：技能槽 4–6、本源槽 2–3，`elfArrow` 固有不占槽。
- 槽位稀缺使三条路线自然长出不同装配哲学（融合求广、异化求深、神化求整），无需额外规则。
- 实施分期：P1 初赐 + 槽位（可立即做，不依赖地图重构）→ P2 深赐 + 共鸣（**数据已就绪，近乎免费**）
  → P3 本源（需新建内容，与第 4 阶段衔接）。
- 移除角色选择流程；清理 `battleRule` 与 `getCharacterAllowedSkillIds`。
- 顺带解决 `CHARACTER_ARCHIVE` 的归宿（赐福详情页）与 `flyingSword` 的归属问题。

### 第 3 阶段 · 地图结构 + 景观模块

- 地图改为主干 + 分叉；分支终点落景观；多奖励轨（景观 / 技能 / 技能强化 / 时装）。
- 景观实装为元地图层光环（完整版主场 + 简化版全局）。
- 工程注意：现有 6×6 网格的 SVG 几何代码（顶点 / 边 / 标签布局）需重写；
  解放逻辑从「4 邻接」改为「父节点解放后解锁子节点」，涉及 `garden-data.js` 区域图与
  `storage.js` 的解放模型。属中等偏大重构，设计需先定死。
- 单角色使「时装」奖励轨成本显著下降（仅一套角色美术）。

### 第 4 阶段 · 技能融合 / 异化 / 神化

- 双技能 / 多技能融合；三条成长分支对应三个剧情方向。
- **关键约束：37 个技能两两组合有 600+ 对，不可手写全部。**
  倾向标签驱动（投射 / 召唤 / 场地 / 状态等 tag 组合推导结果）+ 少量手工打造的招牌融合。
  此决策须在动工前确定，否则本阶段会失控。
- 数值重做并入本阶段（见「已确定的方向 · 数值」）。
- **前置建议：工程地基**。本阶段需改动技能释放的分发逻辑，
  建议先拆分 `game.js`、补单测（波次编排 `rollWaveOrder`、升级池 `buildUpgradeChoices`、
  `storage.js` 的 merge / 迁移、邻接解放逻辑——均为不依赖渲染的纯函数，最易测也最怕回归），
  并引入构建（顺带把 Pixi 本地化，解决离线问题）。

### 第 5 阶段 · 状态联动

现有技能已覆盖灼烧、减速、麻痹、易伤、流血、寄生等状态，但彼此不交互，缺的只是规则表。
**与第 4 阶段共用同一套 tag / 状态基础设施**，建议紧邻或合并实施。

### 第 6 阶段 · 建模优化 + 打击 / 死亡特效

冰冻碎裂、腐蚀融化、击飞、压扁等。依赖状态系统先存在，故排在状态联动之后合理。
建议提前插入一个廉价手感补丁（受击闪白、伤害数字；震屏已有），

## 低成本长尾（不需新增内容，可随时插入）

- 难度阶梯 / 诅咒层：玩家自主加压换收益。无限延伸、成本极低，也是数值失控的正解之一。
- 每局随机 modifier / 固定种子挑战：复用现有波次词条接口，重随「规则」而非「内容」。
- 要求特定构筑的成就：逼玩家走平时不走的路线，把已有内容重新激活。
- 排行榜 / 每日种子：靠他人提供新鲜感，唯一真正可再生的来源。
